## Outcome and confirmed decisions

The existing local operator connects one Google account through the existing Connect flow. Aurvin discovers the calendars exposed to that account through Google's authorized calendar-list surface, uses primary automatically unless a default override is saved, routes explicit calendar requests safely, and checks cross-calendar availability before creating one ordinary timed event. No calendar ID copying, target `.env` editing, or backend restart is required for normal connection or default selection.

The user explicitly selected:

1. **Full multi-calendar:** discover accessible calendars, check their availability where permitted, and create on owned or shared calendars where the connected account has write access. Exact Google scope requirements were a research gate, not a verified fact in the roadmap; **research resolved them on 22 October 2026 and this goal now records the verified least-sufficient set**: `openid`, `email`, `calendar.calendarlist.readonly` (listing), `calendar.events` (reading and creating owned **and shared** events — `calendar.events.owned` fails on shared calendars and must not be used for this goal), and `calendar.freebusy` (availability — `calendar.events` does **not** authorize `freebusy.query`). The broad `calendar` scope and the broader-than-needed `calendar.readonly` remain forbidden.
2. **Target precedence:** explicit calendar request → saved default override → primary. Multiple calendars alone do not require a question. Ambiguous, unknown, or unavailable explicit targets require clarification; do not silently substitute a different target.
3. **Conflict behavior:** ask before proceeding when a conflict exists or complete availability cannot be established. Proceed only after explicit acceptance tied to that event/time and the disclosed conflict or coverage limitation, or after the user chooses another time.
4. **Architecture:** extend the existing embedded MCP plugin with bounded discovery/cache, operation-specific capability checks, and the existing durable runtime. Do not introduce a separate routing service or connector platform.

“One-click” is the user-facing connection experience after operator setup, not zero infrastructure configuration: backend OAuth client credentials, exact callback/origin configuration, encryption material, enabled capabilities, and approved external-processing policy remain necessary. Authentication, RBAC, multiple Aurvin users, multiple connected Google accounts, public hosting, and production certification remain outside this phase.

## Discovery, connection, scopes, and migration

1. Discover bounded calendar metadata after OAuth succeeds, with manual refresh and expiry-aware refresh before use. Return canonical calendar ID, display name, primary flag, role, timezone where supplied, and separate effective capabilities for event read, event creation, and availability. Resolve Google's `primary` alias to the account's canonical calendar ID before durable operation admission. `calendarList.list` gives **no completeness guarantee**: a short page together with a `nextPageToken` is valid, so a snapshot is complete only when no `nextPageToken` remains, and a truncated snapshot may legitimately omit the primary entry. `primary` is **at most one** per account, not guaranteed present; resolve it via the entry's own `primary: true` flag, always retain the primary entry when present, and do not assume the `primary` alias equals the account email after a Workspace rename.
2. Capability is the intersection of the current account/grant, permitted scopes, calendar access role, supported API operation, and Aurvin policy. `owner`/`writer` alone is not sufficient proof of current authorization. Readers cannot write; free/busy-only calendars cannot expose event details. Unknown roles fail closed. Do not use write permissions as the gate for event reads. Google also returns the role **`writerWithoutPrivateAccess`** (shared writer without access to private details): it is writable and readable, but private event details are masked. Treat it as a distinct admitted role, or normalize it to `writer` with an explicit `privateAccess: false` flag at ingestion; it must not fail the whole discovery snapshot as an unknown role.
3. Discover calendars exposed by the authorized calendar-list API, including subscribed/shared entries where supported. Do not enumerate arbitrary calendars, change subscriptions, expand groups without verified bounds, or claim discovery of every calendar that could exist in a Workspace. A hidden/deleted/inaccessible entry and partial discovery have explicit semantics.
4. **Resolved by research on 22 October 2026** (`research.md`, commit `5f9c6c5`): the least scopes sufficient for calendar listing, shared event reads/writes, and availability are `calendar.calendarlist.readonly`, `calendar.events`, and `calendar.freebusy` (plus `openid`/`email`), each confirmed against current primary documentation with incremental/re-consent behavior. `calendar.events.owned` **fails on shared calendars** and is not sufficient. Existing grants cannot be widened by a token refresh, so a Phase 1 grant becomes reconnect-required for multi-calendar actions rather than being silently upgraded. The four calendar scopes are classified **Sensitive** (none Restricted): no CASA audit applies, and no verification exemption for external publishing may be assumed.
5. Existing grants without the new permissions remain readable as legacy records and become reconnect-required for new multi-calendar actions. **Research confirmed that an existing grant cannot be widened by a token refresh**, so a Phase 1 grant must transition to reconnect-required rather than being silently upgraded. Denied/partial consent must not be advertised as full capability. Preserve token encryption/AAD, state/PKCE/nonce validation, bounded refresh and rotated-token persistence, browser binding, disconnect/revocation, and account-replacement invalidation. The re-consent flow must request incremental authorization with `include_granted_scopes=true` and `prompt=consent`, and on callback it must **fail closed**: every required scope must appear in the returned `scope` value, and a partial grant (Google presents per-scope choices) stays reconnect-required with an explicit missing-scope diagnostic rather than being treated as a full grant.
6. Persist a bounded discovery snapshot and an optional explicit default in the existing connection storage; reuse typed metadata for bounded pending proposals/approvals where needed. No new collection is required by this design. Snapshot completeness, fetch/expiry times, and revisions must be explicit. A failed/partial refresh cannot silently replace a complete snapshot with an apparently authoritative subset. Last-known names may be displayed as stale; they do not authorize dispatch.
7. New connections have no manual override and use canonical primary. On explicit versioned migration, an existing Phase 1 connection retains its old pinned calendar as its saved default, preventing a surprise move to primary. Same-account re-consent preserves a still-valid explicit override; account replacement resets preferences to the new account's primary and never carries another account's calendar authority forward. The operator can clear an override. The legacy `AURVIN_GOOGLE_CALENDAR_TARGET_ID` must no longer be required or control new targeting; a documented deprecation path accepts existing configuration without allowing it to override persisted settings or retarget operations. **Research confirmed that a saved-default change must not bump the connection revision**, because that revision currently fences in-flight operations, cursors and checkpoints; the default setting therefore needs its own `defaultSettingRevision`, separate from `connectionRevision`, so a preference change does not invalidate unrelated in-flight work.
8. Read legacy records, operations, receipts, and checkpoints without fabricating new scopes, primary flags, or creation evidence. Plan versioned compatibility and rollback before writes of the new format; verify on isolated fixtures. No implicit application-data migration or transaction with Google is assumed. Unresolved Phase 1 operations remain pinned/quarantined and cannot become a fresh Phase 2 create. **Research confirmed** the required version advances: the tool revision `google-calendar.v1`, the proof revision `google-calendar.events-owned.v1` and the cursor version all advance, with legacy v1 records admitted **read-only**. Non-terminal v1 operations (`planned`, `pending`, `resumable`) must fail closed to a terminal `failed`/`cancelled` state, while completed v1 receipts stay renderable. No new collection is required: the eight existing collections already cover the snapshot, default-setting revision and typed proposal evidence.

## Target selection and conversational authorization

An explicit request names a calendar or selects one through a valid current proposal. Unique exact names can resolve directly. Case/spacing and ordinary wording variations may be normalized; semantic/fuzzy suggestions must not invent aliases or turn uncertain intent into authority. Duplicate names, multiple plausible matches, an unknown name, or a named target with inadequate rights produce a brief, bounded clarification. Distinguish duplicate-name options using safe account-local metadata.

If no calendar is named, use a valid saved override, otherwise primary. If a previously saved override becomes unavailable or loses write permission, ask the operator to choose/reset it; do not silently fall back to primary. If primary cannot be established, ask rather than guessing. The optional picker offers writable defaults plus “Use primary automatically”; readable/non-writable calendars remain visible with their role and reason they cannot be selected for creation.

A sufficiently explicit accepted natural-language scheduling request may authorize its validated canonical action on the resolved target; a mandatory JSON echo or redundant calendar-choice question is not part of the new UX. Missing/ambiguous date, time, timezone, target, or material event details still requires clarification. Do not invent details. Preserve existing timezone/DST and unsupported-feature validation.

Follow-up calendar choices and conflict approvals use bounded durable proposal evidence linked to the originating accepted user message, canonical event, calendar/account/connection, and relevant discovery/availability revisions. A reply can resolve only its current unexpired proposal in the same session. Define safe rejection of stale, replayed, conflicting cross-tab, cross-session, account-replaced, and materially edited proposals. Multiple tabs remain the same operator; they do not receive independent approval authority. A model-provided `confirmed: true`, calendar name, or conflict override flag is never proof of user approval. Normal affirmative/choice replies must be usable without asking the user to copy internal JSON or identifiers.

After clarification, the accepted intent and eventual external operation retain causal linkage across turns. Repeated approval, submission retry, or recovery cannot create another operation. A genuinely new accepted request remains a new intent; no text-similarity deduplication is introduced. Finite per-turn budgets are not silently reset within a retry, and expired proposal evidence is never reconstructed as authorization from free-form history alone.

## Availability and conflict handling

Use a bounded availability/free-busy projection rather than deriving “free” from the existing timed-event list, which omits all-day events. **Resolved by research on 22 October 2026** (`research.md`, commit `5f9c6c5`): provider “busy” is event-driven and opaque — it covers timed opaque events, tentative events (indistinguishable from accepted), recurring events (expanded server-side), **opaque** all-day events, and `outOfOffice`/`focusTime` (opaque by default); private and confidential entries contribute only start/end, never summary or attendees. It does **not** cover `transparency: "transparent"` events (invisible to free/busy, and the default for UI-created all-day events), declined or cancelled events, or working hours, nights and weekends, which are never busy. Aurvin must not present "free" as covering those gaps; it is a conflict signal, not a schedule. Ordinary event creation remains one-off and timed even though conflict checks must account for other busy-event types.

For an explicit range, report busy/free intervals and coverage across the discovered authorized calendar set. Per-calendar errors, stale/incomplete discovery, response-size or calendar-count limits, unsupported entries, quota failures, and unavailable data produce **incomplete/unknown coverage**, never an all-clear. Provider per-calendar failures arrive inside an **HTTP 200** response body (`calendars[id].errors[]`), so Aurvin must classify them as `error` coverage and must never read that response as an all-clear. `freebusy.query` accepts a **hard maximum of 50 calendars per request**; a scan of up to 100 calendars must therefore be batched into at most two requests of ≤50, each counted against the per-turn calendar-request budget. The `groups` expansion parameter is not usable for Aurvin, and the usable query window is far shorter than a month range. Minimize private data: availability does not require unrelated event titles or descriptions. Bound interval merging, timezone conversions, batching, and query ranges.

Every proposed create goes through a **server-enforced preflight** even if the model omits an availability tool call. A conflict or incomplete coverage pauses creation and asks the user to accept the disclosed condition or choose a different time. Missing write authorization for the target is never an overridable availability warning.

Recheck current target capabilities and fresh availability immediately before an undispatched create. Conflict acceptance is tied to the canonical event/range/target and a bounded fingerprint of the disclosed conflict/coverage condition. A material new conflict, changed coverage limitation, changed calendar set, target, time, account, or expired proposal requires renewed confirmation. Do not ask again merely because the same accepted condition was re-read unchanged. Respect the same remaining deadline/request limits during the recheck.

Google availability and event insertion are not atomic; this is conflict awareness, not a reservation, universal no-clash guarantee, or calendar lock. If a create has already been dispatched and its outcome is uncertain, reconcile the original ID/target before considering any further action. Do not run a new preflight as a reason to replay a possibly successful create.

## Tool, API, runtime, and UI contracts

Keep the existing curated, version-pinned embedded MCP path; no public MCP endpoint or arbitrary service URL is added. The model-facing and actual MCP catalogue share the same authoritative schemas and revision. Proposed exact tool surface:

- `calendar_list_calendars`: bounded/paginated names, canonical IDs, roles, capabilities, and freshness/completeness metadata.
- `calendar_check_availability`: explicit bounded range, server-bound authorized discovery set, busy intervals and honest coverage/conflict status; no arbitrary account or unrestricted calendar enumeration input.
- Existing `calendar_list_events`, `calendar_get_event`, and `calendar_create_event`: optional `calendarId` selector where meaningful, resolved server-side using the approved precedence. This includes `get_event`, not only the two methods shown in the roadmap. An explicit ID is an untrusted selector within current capabilities, not an identity/credential override.

Freeze exact schemas, pagination, result provenance, request categories, revision compatibility, and failure codes in P1 after research. Replace the existing blanket prohibition on `calendarId` only at the permitted selector fields; keep identity, tokens, connection/credential revisions, arbitrary URLs, operation IDs, notification flags, and unsupported write fields server-owned. Preserve strict JSON/envelope validation, bounded structural repairs, policy-versus-clarification errors, and safe result rendering. **Research confirmed the five-tool surface fits the pinned `@modelcontextprotocol` 2.3.1 client/server with no new dependency**, with one caveat P1 must honor: the MCP SDK auto-validates `structuredContent` against the registered output schema, so the existing success-result schema must be extended with the two new result schemas or every new tool call fails at runtime. The revision constants must advance together so stored v1 records stay decodable, and the model-facing catalogue and the real MCP catalogue must remain one authoritative surface.

Provider error handling must classify by meaning, not by status alone. **Research confirmed**: `429`, `5xx`, and `403` responses carrying `rateLimitExceeded`/`userRateLimitExceeded` are retryable within the existing bounded delivery-retry budget; `400`, `401` (after a single refresh attempt), `403` `insufficientPermissions`, `403` `quotaExceeded` and `404` are terminal. A `404` on one calendar is a per-calendar failure and must not disconnect the connection. `calendar_create_event` must remain non-retryable so a create can never be silently duplicated.

Separate connection identity/revision, discovery/capability freshness, default-setting revision, and resolved operation target authority. A preference change affects future unresolved work, not a persisted operation's target. Before first dispatch, stale unresolved defaults/proposals must be revalidated or clarified; after dispatch, retries/readback use the original calendar and event ID. Recheck revocation/current rights without substituting the latest default. Account replacement must never permit recovery on the replacement account.

Retain durable acceptance, operation-first dispatch, stable event IDs, matched readback, explicit succeeded/failed/unknown outcomes, complete tool-call/result context groups, per-dispatch attribution/accounting, no private reasoning, one active attempt per session, and safe cancellation/drain/fencing. Preserve completed receipts even if final narration fails. A calendar badge/name is derived from durable operation evidence, not provisional model prose or the current default; apply existing content-expiry rules to that metadata.

Extend existing routes under `/api/plugins/google-calendar/`:

- `GET calendars`: bounded cached discovery with capabilities, freshness, completeness, and pagination; no effectful refresh hidden in a status/liveness probe.
- `POST calendars/refresh`: explicit bounded refresh, protected by the existing local mutation boundary.
- `PATCH settings`: retain enable/disable behavior and add optional default selection/reset, revision conflict handling, and server-side capability validation. It must be possible to change only the default without accidentally toggling enablement.

Update the existing frontend client/protocol, setup reducer/panel, and chat receipt/progress region. Cover loading, empty discovery, reconnect for added permissions, stale/partial results, refresh failure, inaccessible saved default, save conflicts, disabled state, and rollback after failed saves. Use existing styling and native accessible controls; preserve focus, labels, announcements, drafts, and existing text/voice/canvas behavior. No client-side identity, credentials, or authorization decision is added.

## Finite limits, privacy, and operational behavior

Retain the existing upper limits: 8 model dispatches, 2 structural repairs, 6 logical model-requested tools, 1 logical create, 20 Calendar HTTP requests and 2 refresh-token requests per accepted turn, 2 eligible delivery retries, 31-day event/availability ranges, 20 events per result, 16 KiB arguments/results, 20-second tool calls, existing 180-second default total deadline, and USD 1 estimated model-spend admission. Lower configured limits still apply. All discovery/preflight/batching/rechecks/reconciliation requests have explicit accounting; internal preflight does not masquerade as another model-requested logical call.

New finite ceilings, **compatibility-checked by research on 22 October 2026** (`research.md`, commit `5f9c6c5`) and to be frozen by P1 before downstream work. Research may recommend smaller bounds; a ceiling is never raised to fit an API response.

- At most 100 retained calendar entries, at most 20 calendar entries per UI/tool page, with encoded byte limits taking precedence. Overflow is explicit partial coverage with continuation where supported, not silent truncation or an unbounded fetch loop. Discovery page deliveries: always request `maxResults=100`, and allow at most **2 in-turn** page deliveries (an in-turn refresh must not consume half the 20-request per-turn budget); the ceiling of 10 page deliveries applies only to out-of-turn refreshes (OAuth install, explicit UI refresh).
- Discovery freshness at most 5 minutes, reduced by stricter provider/cache/privacy rules; no long-lived cache annotation establishes permission. Fresh operation-specific checks remain necessary.
- At most 100 calendars per availability scan, **batched into at most 2 `freebusy.query` requests of ≤50 calendars each** because the provider hard-limits a request to 50; each delivery counts against the per-turn calendar-request budget. At most 2,000 busy intervals **processed** as a provider-response ingestion ceiling, but the **returned** payload must coalesce overlapping intervals and stay within the existing 16 KiB result budget (≈15,360 usable bytes), otherwise it is marked `truncated` with incomplete coverage. At most 256 KiB of discovery/availability working or persisted snapshot data, further reduced by existing document/response budgets. An incomplete/oversized result cannot claim complete availability.
- Pending proposal lifetime at most 10 minutes, one current proposal per session, bounded records with expiry/tombstone and single-consumption semantics. Lifetime expiry cannot erase unresolved-operation deduplication evidence.

Research may recommend smaller or technically different bounds, but must report changes for goal/state reconciliation before planning. Never silently raise these limits to fit an API response. A request that exceeds a budget returns the appropriate limit/coverage/clarification outcome instead of dropping histories or claiming success.

Treat calendar names, metadata, links, provider errors, and results as untrusted data. Do not let calendar/event content inject instructions or select another identity/target. Reuse approved source-linked retention, stricter cache/header lifetimes, redaction/tombstones, safe backups, encrypted tokens, sanitized logs, and approved Google/OpenRouter/provider processing policy; verify whether metadata caching and shared-calendar data need additional policy changes. No stronger retention or “fully local” claim follows from this phase.

Keep plugin default-off, local Host/Origin/CSRF protections, ordinary text chat when Calendar is degraded, non-paid liveness/readiness, one native MongoDB single-process executor, ownership/drain and uncertain-write handling. Keep live-voice tools disabled. Default changes and discovery refresh do not require restart, replace the executor, delete events, or provision anything.
