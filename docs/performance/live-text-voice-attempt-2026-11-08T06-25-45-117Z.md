## Failure cause and correction prepared

The operator caller omitted the required `Origin` header. The existing benchmark
`runText` supplies only `Content-Type`; the actual Calendar-enabled chat boundary
requires exactly the configured frontend origin for POST and for headless GET
requests. Its rejection path returns HTTP 403 before chat acceptance. This was a
benchmark caller preparation error, not evidence of model or voice failure.
No error response payload, prompt or transcript was emitted.

The one-off caller had negotiated the server-required `calendarProtocol: 2`
because the checked-in runner hardcodes 3 while the actual Calendar-enabled HTTP
route admits 2. This is recorded as a client compatibility adaptation, not a
runtime/source/configuration change or frontend protocol-3 validation.

A separate corrected operator script now supplies `Origin: config.origin` for
all text HTTP requests. Its syntax check passes. It has **not been executed** and
is not a verified live fix; further live behavior, including other boundary
requirements, remains unverified. The as-run script and all original evidence
