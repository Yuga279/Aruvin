## Task 4 voice implementation and capacity resolution

Ordinary live turns use the **same** `MemoryText`/`MemoryFirstFoundation` instance as text, selected through `RuntimeDependencies.memoryFirst.voice`. The native `AppService` composition enables this route when `persistence.owner.store` is present, falls back to the durable route when a lightweight injected `open` stub omits `owner.store` with `memoryFirstPolicy === undefined`, and fails closed when an explicit `memoryFirstPolicy` is supplied without `owner.store`. `memoryFirstPolicy: null` still selects entirely durable composition.

- **Turn admission, delivery & heard vs generated boundaries**: The bridge supplies trusted voice session/socket epoch/provider-turn identity and identifies a fresh derived conversation before binding it. Warm reservation checks and turn admission use memory; cold admission hydrates trusted storage. Calendar-enabled snapshots/references and cold Calendar provenance retain the durable route, failing closed on dirty memory. Voice execution uses existing `SpeechProse` and `VoiceDelivery`, flushing TTS synthesis immediately at `prose.visualSuffixStarted` so Canvas Markdown never enters speech synthesis. Proven spoken text, generated text and unknown hearing remain distinct: failed or unstarted settlement records **unknown with null spoken evidence**, never an invented heard prefix, and the next eligible voice utterance uses only proven heard prose (or omits unproven answers).
- **Exact measured live output reservation (resolving prior `maxEvidenceBytes / 24` ceiling)**:
  - Traced all retained live copies (`SpeechProse` spoken/visual buffers, `VoiceDelivery` terminal generated/spoken/Canvas/proof payload, `MemoryFirstFoundation` envelope `input`/`output`/`evidenceBytes`/fixed overhead, and `MemoryText` active turn/message projection).
  - Replaced the crude `floor(maxEvidenceBytes / 24)` (682-byte) and `floor(maxOutputBytes / 6)` caps in `backend/src/chat-runtime/memory-text.ts` with `checkOutputCapacities`, measuring exact incremental JSON-escaped UTF-8 byte lengths (`escapedJsonBytes`) across generated text, spoken text, Canvas raw/projection bytes, and terminal evidence (`voiceEvidenceBytes`), and updated `MemoryFirstFoundation.complete()` to include `canvasArtifacts` in output byte validation.
  - Updated **proposed** `PROPOSED_MEMORY_TEXT_POLICY.maxEvidenceBytes` from `16_384` to `131_072` (128 KiB, bounded inside existing `maxEnvelopeBytes = 524_288` and `maxMemoryBytes = 67_108_864`) while preserving **approved** `DEFAULT_BUDGETS.maxMessageBytes = 65_536` and `CANVAS_ARTIFACT_LIMITS` (`maxProjectionBytesPerTurn = 32_768`, `maxRawCandidateBytes = 40_960`, `maxStoredArtifactsPerMessage = 3`).
  - **Deliberate remaining live output ceiling & operator sizing**: Before paid inference/TTS begins, live admission enforces the `8_192`-byte `maxEvidenceBytes` floor, reserves envelope memory in `MemoryFirstFoundation`, and reserves `messageReserveBytes = CANVAS_ARTIFACT_LIMITS.maxProjectionBytesPerTurn + 1_024 = 33_792` bytes inside `maxMessageBytes = 65_536`. This permits up to **`31_744` JSON-escaped UTF-8 bytes** of spoken prose alongside up to **`32_768` bytes** of Canvas projections without overflowing message, output, or evidence budgets under worst-case Unicode/quote escaping. Operators lowering `maxEvidenceBytes` or `maxOutputBytes` tighten `checkOutputCapacities` proportionally before overflow.
- **Bounded clean voice-observation & clean-session reclamation (resolving prior 128-observation restart ceiling)**:
  - Each `observeVoice` entry reserves `observationBytes() = Math.min(4_096, policy.maxEvidenceBytes)` prior to paid socket/speech setup and shares turn-save concurrency, backlog, raw-promise tracking, retry budget, and shutdown drain via `SaveVoiceObservation`.
  - Saved clean observations record `retainUntil = now + requestRetentionMs` and a monotonic `savedOrder`. `evictCleanObservations` sweeps expired clean entries, and `reclaimCleanObservations` evicts the oldest clean (`state === 'saved' && recorded !== null`) entry by `savedOrder` when `observeVoice`, `accept`, or `hydrate` reaches `maxRequestsPerSession` (`128` proposed) or `maxMemoryBytes`.
  - `MemoryText.evictCleanSessions` reclaims idle clean session overlays (`turns.size === 0`, no active reservation, no dirty state, and past `requestRetentionMs`) once foundation turns/observations for that session are clean.
  - **Pinned safety**: Any observation or turn in `pending`, `saving`, `failed`, `unknown`, `fenced`, or unrecorded in-flight state is **never evicted**. Deduplication remains exact for all active/dirty records and retained clean records; if 128 dirty/unknown observations accumulate in one session or dirty bytes exhaust `maxMemoryBytes`, new paid work fails closed with `NOT_READY` rather than dropping unsaved evidence.

## Task 5 browser recovery, live save UX, retry transport recovery and navigation busy restoration

- **Ordinary submit & generation-retry transport recovery (`ApiClient`)**:
  - `ApiClient` retains at most one bounded ambiguous recovery record (`pendingSubmission` **or** `pendingRetry`, mutually exclusive, 200,000-character storage guard, strict schema/ID validation) in tab `sessionStorage` with in-memory fallback when storage is unavailable.
  - Lost/aborted/5xx ordinary `POST /sessions/:sessionId/turns` requests retain `{ sessionId, idempotencyKey, payload, expectedEpoch }`; lost/aborted/5xx generation-retry `POST /sessions/:sessionId/turns/:turnId/retry` requests retain `{ sessionId, turnId, idempotencyKey, expectedEpoch }`.
  - `retryTurnRequestSchema` (`backend/src/contracts/api.ts`), `DurableChatRuntime.retryTurn`, `MemoryText.retry`, and `ChatHttpService.retry` accept and enforce optional `expectedEpoch` (checked before session lookup so unknown post-restart sessions return `409 INTERRUPTED` rather than `404`, and `DurableChatRuntime.retryTurn` joins in-flight acceptance on same-epoch replay).
  - Replaying a recovered retry reuses the **exact original `idempotencyKey` and `expectedEpoch`** across client reloads, blocks conflicting ordinary submits or retries on other turns/sessions, clears automatically on definite `4xx` (`INVALID_REQUEST`, `SESSION_NOT_FOUND`, `TURN_NOT_FOUND`, `SESSION_BUSY`, etc.), and retains unknown state on `409 INTERRUPTED` until the user explicitly chooses **Retry original request** or **Allow a new attempt** (with repeat-generation/charge warning). `retrySave` never resets or alters `pendingSubmission`, `pendingRetry`, or foundation retry budgets.
- **Live voice pending sidebar row & live save notifications**:
  - Extended `conversation.bound` (`backend/src/contracts/voice-wire.ts`, `frontend/src/api/voice-protocol.ts`, `backend/src/voice/agent/agent-voice-adapter.ts`) with paired optional `{ turnId, save }` emitted at live acceptance and re-emitted after `await active.done` settles.
  - `BIND_VOICE_CONVERSATION` (`frontend/src/features/chat/state/chat-reducer.ts`, `useLiveVoice.ts`, `live-voice-controller.ts`, `App.tsx`) creates an optimistic `New chat` sidebar row tracked in `localSessionIds` (surviving stale `listSessions` responses until durable persistence catches up) and dispatches session-scoped `SAVE_STATE` (`mode: 'live'`).
  - While `liveActive` is true, `ChatView.tsx` renders an operational live save status notice (`Saving this chat in the background…` / failure / unknown warning + `Retry saving` button wired to `POST /sessions/:sessionId/turns/:turnId/retry-save`) without mounting the text `<textarea`, leaking drafts, or rendering the ordinary text transcript, and `copyConversation` exports `voiceTranscripts` when message rows are not yet loaded.
  - `startSavePollEffect` (`frontend/src/features/chat/state/use-chat.ts`) polls at most 10 bounded intervals (`250 ms`), using `listMessages(sessionId, { limit: 1 })` when `mode === 'live'` (because live turns fence public `getTurnStatus`) and `getTurnStatus` when `mode === 'text'`, canceling timers on settlement, session switch, or unmount. Same-call follow-up utterances under blocked saves advance `turnId`/save versions monotonically via `(epoch, version, durableVersion)` ordering.
- **Busy-state restoration across session navigation**:
  - `ListMessagesResponse` (`backend/src/contracts/api.ts`, `frontend/src/api/protocol.ts`, `MemoryText.messages`, `DurableChatRuntime.activeSessionTurn`, `ChatHttpService.messages`) now carries optional `saveTurnId` and `activeTurn: { turnId, status: 'accepted' | 'generating' | 'finalizing', mode: 'text' | 'live' }`.
  - Switching away from an active turn mid-generation aborts the foreground stream cleanly, and navigating back loads `activeTurn` via `MESSAGES_LOADED`, restoring `activeTurnId`, `turnStatus`, and `activeTurnMode`, gating conflicting `submitMessage`/`retryTurn`/`claimVoiceInput`/composer controls, and running `startRestoredBusyPollEffect` (bounded polling via `getTurnStatus` for text or `listMessages(limit: 1)` for live) with deterministic timer cleanup on terminal arrival, session switch, or unmount.

## Recovery and deployment admission

Memory/accounting can be lost on process death; no disk spool was added. Complete publications remain durable-graph compatible. Partial cold publication is an **unknown/unavailable outcome**: keep/export a browser copy, inspect surviving records under the documented ownership procedure, and do not infer non-dispatch from absent data or replay inference automatically. Save-only retries reconcile retained immutable records by stable IDs and preserve raw-write ownership without resetting retry budgets.

Before deployment, an operator must supply actual host memory/headroom and throughput facts, approve concrete memory/evidence/observation-retention ceilings (`PROPOSED_MEMORY_TEXT_POLICY` remains **proposed**, whereas `DEFAULT_BUDGETS` and `CANVAS_ARTIFACT_LIMITS` remain the existing **approved** message/artifact limits), set graceful termination drain budgets, and enforce single-process rollout. The actual Azure product/API/tier remains unknown (`R1`); native replica-set and Azure capability certification require separate operator authorization and isolated service checks. Browser layout, accessibility, and real LiveKit/Deepgram/OpenRouter latency were not measured in this Node/sandbox pass.
