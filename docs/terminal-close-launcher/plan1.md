# Plan 1 — console-independent Windows backend launcher

Status: executable implementation plan; no implementation or application run in planning. Approved scope: [goal.md](goal.md). One worker, no reviewer; review **skipped**. Preserve unrelated work and the existing blocked database.

## Findings and chosen minimum

- `run.bat:72` currently starts the backend inside `cmd /k`; closing that console can kill the executor. Keep ports 8001/5179, backend cwd, one compiled build, frontend launch and browser behavior.
- `backend/src/main.ts:55` observes IPC only after `listen()`. Sending `shutdown` earlier is unsafe: it can be lost. Existing `app.close()` reaches `OperationsService.beforeApplicationShutdown()`; that service already makes stop/drain/persistence-close idempotent and sets a failing exit code on unsafe close. Reuse it, not a second runtime or close owner.
- Use only Node standard library: one uncompiled ESM launcher with `start`, `supervisor`, and `client` modes. Separate supervision from the visible `cmd` process. No dependency, watch process, daemon service, HTTP administration route, log file, database work, recovery automation or restart.

### Windows semantics verified on 8 October 2026

Planning environment: Windows, Node v24.18.0, libuv 1.52.1. Current Node 24 documentation was queried through Context7; documentation is not a Windows smoke pass.

1. [Node child processes](https://nodejs.org/docs/latest-v24.x/api/child_process.html#optionsdetached): detached processes can outlive the parent; ignored stdio and `unref()` are required for an independent launcher. `windowsHide` only promises hiding, not isolation.
2. [Pinned libuv Windows implementation](https://github.com/libuv/libuv/blob/v1.52.1/src/win/process.c): detached adds `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`; non-detached children are normally placed in the parent's kill-on-close job. `windowsHide` adds `CREATE_NO_WINDOW` only when no stdio entry inherits an fd. Do not use inherited backend stdio.
3. [Microsoft creation flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags): `DETACHED_PROCESS` does not inherit the console; `CREATE_NO_WINDOW` has no console handle and is ignored with `DETACHED_PROCESS`. Thus coordinator isolation is detachment, while backend isolation is non-detached + hide + fresh pipes/ignored stdin. These are intentionally different mechanisms.
4. [Node net IPC](https://nodejs.org/docs/latest-v24.x/api/net.html#ipc-support): Windows named pipes disappear when references close. [Console creation](https://learn.microsoft.com/en-us/windows/console/creation-of-a-console) and [console closure](https://learn.microsoft.com/en-us/windows/console/closing-a-console): a console client is disposable; do not try to perform the backend's drain inside its close handler.

Node's wording about a detached child's own console is not enough to infer exact host behavior; pinned libuv and Win32 flags explain the intended no-console setup. Verify the actual installed Node/terminal combination below. External restrictive Job Objects can still kill detached descendants; Node does not request `CREATE_BREAKAWAY_FROM_JOB`. No promise for IDE/CI job hosts, machine shutdown or forced supervisor death.

## Implementation sequence

### 1. Fix bootstrap's shutdown race, with focused tests first

- In `bootstrap()`, install the IPC message listener before env loading and the first await. Once installed, send an allowlisted `shutdown-ready` acknowledgement when IPC is connected. Coordinator must never send `shutdown` before this ack: even module-import time is covered by its pending-stop latch.
- Latch `shutdown` while `NestFactory.create()`/configuration/listen is unresolved. After creation, check the latch before configuration/listen and between awaited startup stages; skip listen if stop was already requested. Never race `app.close()` against an unresolved `listen()`; close immediately once that stage settles.
- Use one memoized close promise for IPC and startup catch cleanup; duplicate requests cannot call `app.close()` twice. Retain existing Nest signal hooks for direct-launch behavior, startup allowlisted diagnostics and extensionless entry support.
- On successful listen, send a distinct `backend-listening` ack only if not stopping. This is listener readiness, not chat/database readiness. On close completion/failure retain exit code behavior and disconnect IPC; coordinator judges exit code/actual process exit, not text output. Remove installed listeners on failed/completed lifecycle where necessary so the IPC channel cannot keep startup failures alive.
- Do not invent cancellation of Nest creation or free a partially created application's database. A stuck creation/listen is stopped by the external deadline and is explicitly unsafe.

### 2. Launch and supervise independently

- `start` (called by `run.bat`) mints a random per-launch pipe name and 256-bit capability, passed to the supervisor by environment, never argv or files. Spawn supervisor via `process.execPath`, absolute script path, backend cwd, `detached:true`, `windowsHide:true`, `stdio:'ignore'`; observe spawn error, then `unref()`. No inherited terminal or persistent parent IPC channel.
- `start` connects to that private pipe with bounded retries. Supervisor accepts two authenticated roles, one starter and one console. Starter disconnect before successful launch means startup abandoned: stop any owned backend. After success its disconnect is normal. Supervisor starts its own 45-second overall startup timer immediately, including pipe/client attachment; loss of starter or absence of a client cannot leave an executor unattended.
- Supervisor starts visible `cmd.exe /d /v:off /s /c` from its no-console process, `detached:false`, `windowsHide:false`, ignored stdio. With no parent console, this console executable should receive a new visible console; test this instead of assuming `start /b` or hidden windows isolate it. The command runs **only** the Node client, no `/k`, `pause`, batch wrapper or shell fallback.
- Pass Node/script paths through quoted environment expansions, not interpolated shell commands; avoid `call` (second expansion). Client environment is an OS-variable allowlist plus its pipe/capability/path values, not inherited database/provider secrets or `NODE_OPTIONS`. Test spaces, `&`, `%`, parentheses and `!` in checkout paths. Never interpolate user message/configuration contents into the command.
- Ignored stdio means client stdout is not the screen. Client must explicitly open `CONOUT$` for display; opening it and authenticating successfully are prerequisites to its `attached` message. If that fails, exit nonzero and stop startup. Do not claim the visible console works by merely spawning cmd successfully.
- Only after authenticated console attachment fork the actual compiled `dist/main.js` once: `execArgv:['--enable-source-maps']`, backend cwd, `detached:false`, `windowsHide:true`, `stdio:['ignore','pipe','pipe','ipc']`. No console fd is inherited; libuv's `CREATE_NO_WINDOW` path applies. Keep process/IPC references alive until backend exit. Backend receives the original app environment/PORT/origin, excluding launcher capabilities; `.env` loading remains in main.
- Supervisor observes backend spawn/error/exit/IPC disconnect and console socket/cmd exit/error from the moment each handle exists. Cmd exit catches closing even before authentication; an attachment deadline catches hung/missing clients. Backend is never restarted. Startup failures stop all owned children and return one static diagnostic to the starter; never print exception objects, environment or capability.
- Starter succeeds only after this launch's `backend-listening` ack and a bounded `/api/operations/live` response on the configured loopback port. Thus an unrelated old listener cannot falsely satisfy launch success. Put this existing liveness gate inside launcher start so its timeout requests cleanup over the still-private pipe; `run.bat` checks launcher exit code before unchanged frontend launch. The supervisor's own startup deadline remains authoritative if starter dies.

### 3. Private local attachment and bounded display

- Pipe uses `\\.\pipe\aurvin-terminal-<random>`; no TCP control listener, discovery file, fixed/shared name or database identifier. Use default pipe permissions, never `readableAll`/`writableAll`. First frame authenticates capability and role; reply authenticates the server with the same capability before accepting its output. Compare fixed-length tokens with `timingSafeEqual`, reject missing/invalid tokens and duplicate roles without stopping a legitimate launch.
- Capability is the security boundary, not pipe-name secrecy or an assumed Node per-user ACL. Same-user/admin process inspection is outside the local launch boundary; named pipes are not an authenticated public service or a guarantee of remote-client rejection. Do not expose/share pipe credentials. No backend keys or user identity are part of this protocol.
- Bound unauthenticated sockets (maximum four, two-second auth timeout, maximum 4 KiB first/control frame); reject malformed/unknown commands. One attached client only. Stop the listener after the two launch roles attach; retain their connected sockets. Do not let unrelated connections reset deadlines or trigger stop.
- Use tiny newline-delimited JSON control/output frames; maximum 32 KiB frame, split backend output into at most 8 KiB chunks. Logs are live only: no file, transcript, startup replay or unbounded output array. Continuously drain both backend streams even without a console.
- Check pipe/client writable queue before each output write (64 KiB ceiling plus one bounded frame); drop log chunks under backpressure and show one bounded loss notice when writable again. Bound client console-write buffering too; backpressure must not stall backend drain or grow memory. Stop/status frames have reserved bounded handling or close the failed client and request stop rather than indefinitely queueing them. Mark intentional live-log loss with a `ponytail:` ceiling/upgrade comment.
- Client SIGINT requests `stop` once and waits for backend exit status. Repeated Ctrl+C must not race multiple stop paths. Actual window close need not run JS: socket EOF or tracked cmd exit is sufficient. Supervisor finishes independently of that console. Normal backend exit sends a terminal status; client closes pipe/display and exits, so `/c` ends cmd lifetime. Bound terminal-status delivery to two seconds; don't keep cmd hanging after backend exit.

### 4. One stop path, hard bound, failure cleanup

- All console loss, authenticated stop, startup timeout, starter abandonment and process errors converge on one idempotent stop latch and one **45,000 ms** timer, starting at the first stop request (not at IPC readiness). For an already-spawned backend, wait for `shutdown-ready`, then send existing literal `shutdown` exactly once with callback error handling. An early-close request remains pending across module imports/creation; do not retry inference or relaunch.
- If stop precedes backend spawn, do not spawn it. Startup time and shutdown time are separate finite budgets; startup timeout enters the same bounded stop path.
- Await actual backend exit, including its drain/close. Zero exit after requested cleanup means confirmed graceful application exit; nonzero/disconnect/send failure is not safe confirmation. IPC disconnect alone must not end supervision while backend lives.
- At 45 seconds force-terminate only the tracked owned backend child (`child.kill()` on Windows is not graceful), mark unsafe and require operator recovery. Do not enumerate/kill arbitrary Node processes, use stale PIDs, remove a sentinel, mutate database, take over ownership or auto-restart. Reap owned cmd/client and destroy sockets/timers after backend exits; don't exit the supervisor while its backend remains live. If termination fails, keep the owned handle and report static failure to any surviving starter/client; do not falsely report success or safe cleanup.
- Recoverable supervisor errors use this same cleanup path; a forced kill/crash of supervisor is explicitly outside the guarantee. Do not install an uncaught-exception handler that pretends arbitrary corrupted state is safely recoverable.
