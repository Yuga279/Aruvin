# Local integration research

- The existing Calendar loop already has a volatile stage, a volatile ledger, a lazy promotion hook and an owned durable dispatcher. Reuse these rather than introducing another dispatcher.
- MemoryText.eligible currently rejects enabled Calendar. Durable submit/live/findLiveSubmission have additional reply/config exclusions. Native Calendar execution in MemoryText is text-only; live Calendar currently falls into the plain provider adapter.
- MemoryText.hydrate rejects pending proposals and sourceProvenance. It otherwise validates the durable manifest, settled graph boundary, attempts, archive and native capsules. Remove only the Calendar exclusion and retain consistency checks.
- Foundation retains active turns, prior terminal envelopes, a version/durableVersion pair, per-session ordered jobs and global rawWrites. A save timeout changes visible state without settling/cancelling the raw call. Promotion must wait the actual session write, never start a duplicate while it is unresolved, and fail closed within the write deadline.
- CalendarTurnLedger creates and validates ConfirmedBudget and dispatch receipts using persistence repositories. MemoryCalendarLedger carries no receipt authority. Promotion must materialize immutable dispatch/decision/result records and budget through those repositories, never cast volatile state to ConfirmedRecord.
- Foundation.complete queues a save; promoted completion must use a distinct commitPromoted path that advances both versions, releases the accepted envelope and imports the durable assistant with sourceProvenance without a second archive job.
- MemoryCalendarState currently requires dispatch count equal total budget.modelDispatches and indexes starting at one. Retry seeding must preserve aggregate budget counters while allowing this attempt's contiguous suffix dispatches. Seed money must be retained when recompute processes current-attempt observations.
- calendarHistory presently joins only durable calendarAccountingV2 dispatches. When there are none, reuse readMemoryCalendarStates and memory-calendar-native capsules with their publication/attempt validation instead of guessing local groups.
- Existing persistence/calendar-records.ts offers redactCalendarMessage (time expiry), redactCalendarMessageForAccount and redactCalendarSourceForAccount. Reuse these for warm invalidation. Existing Calendar context assembly already validates groups and sources; use the injected clock rather than Date.now.
- publishCalendarTurn persists assistant, manifest, boundary and terminal attempt, and supports commitBoundary/beforeTerminal hooks. It does not update sessions.memoryPublication. MemoryTextArchive requires that marker's version equal each later envelope.previousVersion, so promoted publication must advance the durable marker and sequence counter while owned, before releasing the lease.
- Core tests already have six eligibility overrides and one real production test; parent reproduced the real failure in acceptNewTurn, while the overridden tests pass. Existing calendarFixture has deterministic provider wires and a fixture store; prefer it and real repository bundle for receipt authority tests.

No production code was changed during research. No external documentation/service request is necessary for this local integration.
