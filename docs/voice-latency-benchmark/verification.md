## Interpretation and remaining gates

**No live OpenRouter, Google Calendar, or Deepgram benchmark calls were made. No real-provider bottleneck has been established.** Fixture throughput must not be presented as LLM tokens/second. No real Calendar event was created, changed, or deleted.

Before a live run:

1. Obtain an explicit spending ceiling and appropriate provider-account spending controls.
2. Obtain Calendar data-processing permission and a known synthetic event; for creation, approve a disposable target and mutation permission.
3. Have the operator safely deploy/restart the instrumented backend and supply its current diagnostic log/revision. Do not overlap database executors.
4. Run the bounded client with explicit live config gates. Report refusals/clarifications, unknown usage, dropped/missing diagnostics, and failed/unsupported cases rather than inventing durations.
5. Measure actual browser/device capture and audible output separately. The current headless voice client uses simulated real-time playback acknowledgments, not an audio device.

The implementation does not exhaust every business-logic branch, follow-up or failure mode with live providers. Its initial scenario set covers one representative workflow per exposed text tool plus no-tool text/voice baselines. Automatically negotiating Calendar clarification/confirmation exchanges is intentionally not implemented; those runs are explicitly incomplete, never counted as successful event creation.
