## Decisions and evidence boundaries

- **Recommend the existing REST integration, not Google's hosted MCP**, as the starting point. The latter is Developer Preview, requires additional enrollment/configuration, and its documented calendar-list result omits role and data-owner evidence. It is not a proven drop-in for Aurvin's authorization, accounting, write recovery or privacy. No new provisioning or scopes are authorized.
- **The reported live failure is unobserved.** We have neither its actual tool arguments nor its rejection boundary. The model's page-token explanation is not evidence. Current code advertises and accepts `{}` for `calendar_list_calendars` structurally, but that does not prove the assembled call or live incident succeeds. In particular, an independently discovered malformed token, incomplete discovery, failed provider request, or any other source path is a hypothesis until a correlated trace establishes it.
- **Ownership is not a simple role filter.** Google explicitly says `owner` is a manager role, potentially held by multiple users, unlike the single data owner. A list of calendars with owner access must be described as such, not automatically as calendars actually owned by the user. See the ownership section below; this affects AC6 and any claim of an accurate owned-calendar answer.
- P1 supplies a safe trace and actionable offline reproducer or an explicit evidence gap; P2 starts only after that handoff. P2 must prove production-assembly behavior and historical compatibility, not remove safety checks based on apparent duplication. Live acceptance remains separately blocked until authorized or explicitly waived for implementation-only scope.

## Google primary contracts

### Calendar list, roles and pagination

[CalendarList.list](https://developers.google.com/workspace/calendar/api/v3/reference/calendarList/list) is authorized `GET /calendar/v3/users/me/calendarList`: it returns the user's calendar **list**, not an exhaustive directory of every accessible calendar. Its optional `pageToken` is Google's token from `nextPageToken`; first page omits it. `maxResults` defaults to 100, max 250; `minAccessRole`, `showDeleted` and `showHidden` are optional, with hidden/deleted defaulting false. `nextPageToken` is omitted at the end; `nextSyncToken` is a different incremental-sync token and must not be confused with paging. The documented list scopes include `calendar.calendarlist.readonly` and broader alternatives.

[CalendarList resource](https://developers.google.com/workspace/calendar/api/v3/reference/calendarList) defines `accessRole` as the effective role: `freeBusyReader`, `reader`, `writerWithoutPrivateAccess`, `writer`, or `owner`. `owner` means manager access including changing others' ACLs, **not** data ownership. `dataOwner` is an email, set only for secondary calendars; `primary` denotes the authenticated user's primary calendar. `minAccessRole=owner` is therefore not proof of data ownership. Missing `dataOwner`, primary vs secondary, account identity/aliases, hidden entries and incomplete pages all require honest qualification rather than a fabricated yes/no. Existing OAuth identity has an account email, but an email comparison's identity/alias semantics and any source-retention implications are not established by the references; do not claim that raw email equality proves all ownership. Exposing `dataOwner` or an inferred field changes a strict result/persistence contract; assess the minimum safe provenance and privacy handling before selecting it. If actual ownership cannot be established under current constraints, answer with the available role/primary evidence and explicit uncertainty; reconcile AC6 rather than silently equating role with ownership.

The following inventory describes current Aurvin contracts and paths, **not** Google's complete capabilities. Local semantic checks and safety policy are additional to JSON Schema. None of these descriptions authorizes new tools or OAuth grants.

| --- | --- | --- |

Result includes calendar ID/label, `accessRole`, `primary`, capabilities, discovery time/revision, completeness/limitations, and nullable continuation. Local token is a signed snapshot offset, not Google `pageToken`; hidden/deleted excluded and capped snapshots can be incomplete. |

Aurvin `calendarId` omission means server resolution/default, not an unconditional claim that Google defaults it; `primary` is a Google-supported alias subject to Aurvin's resolution. Source also imposes size, output and time budgets and blocks reserved/unsafe fields. Descriptions must distinguish these deliberate restrictions and actual projections from Google defaults.

### Scope, errors and preview

`backend/src/contracts/calendar-policy.ts` requires the existing v2 grant set `openid`, `email`, `calendar.calendarlist.readonly`, `calendar.events`, `calendar.freebusy`; it rejects broad `calendar` and `calendar.readonly`, and all listed scopes must be present for `calendarGrantStatus`/capabilities. Google's [scope guide](https://developers.google.com/workspace/calendar/api/auth) recommends narrow scopes; list, event get/list/insert, and freebusy references above list their accepted alternatives. Scope is necessary but not sufficient: account, actual calendar role, policy and server-owned target/confirmation remain authority checks. Do not weaken or expand grants just to match a preview setup.

[Google errors guide](https://developers.google.com/workspace/calendar/api/guides/errors): 400 invalid request is permanent until corrected; 401 may require refresh/reconnect; 403 may be permission, quota or rate limit (reason matters); 429 rate limiting is comparable to rate-limit 403, with bounded backoff; 404 can mean missing **or inaccessible**; 409 event identifier conflict needs careful reconciliation; 410 sync expiration differs from a deleted event; 5xx can be transient. The HTTP adapter currently maps these to bounded internal failures; 400 also maps to `CALENDAR_INPUT_REJECTED`, the same broad code used for some **local** cursor errors. Trace must preserve origin before that distinction is erased. Do not send raw provider error bodies to logs, treat 404 as definitive permission diagnosis, retry permission denial as repair, or repeat an uncertain POST. Google's own retry guidance does not override Aurvin's uncertainty safety policy.

[Google MCP setup](https://developers.google.com/workspace/calendar/api/guides/configure-mcp-server) documents Developer Preview membership, Google Cloud project, Calendar API and Calendar MCP API enabled, OAuth consent/client configured for an AI-powered agent, and Streamable HTTP. Its example read scopes are not a substitute for write authority. It advertises create/delete/get/list/respond/suggest/update, more actions than Aurvin permits. The setup warns about indirect prompt injection. [MCP list_calendars](https://developers.google.com/workspace/calendar/api/v3/reference/mcp/tools_list/list_calendars) has optional `pageSize` (default 100, max 250) and `pageToken`, and returns `id`, `summary`, `description`, `timeZone` and next token; its documented item has **no** `accessRole`, `primary` or `dataOwner`. Do not infer capability or ownership from it. Preview participation, account availability, actual dynamic tool schema and Aurvin-compatible write/recovery have not been verified; no hosted adoption or live test is authorized.

## Current execution, schema and safety boundaries

1. `app.service.ts` and `operations/calendar-assembly.ts` assemble one runtime, credentials, discovery/capability gate, `CalendarApiTools`, and `EmbeddedCalendarExecution`. `CalendarLoop.decide` uses `CALENDAR_TOOLS` for initial, continuation and correction requests; `calendarContext` preserves valid tool/result pairs and checks account/source expiry; `model/calendar-policy.ts` validates catalogue equality and serializes `tools` into the native OpenRouter body. This source path is encouraging but request-body assertions must cover all three production dispatch modes; a scripted model alone is not evidence of live compliance.
2. `model/calendar-validation.ts` scans JSON with limits, rejects multiple/unknown/forbidden calls and maps Zod issues into bounded repair diagnostics. It hashes raw arguments for persisted rejection evidence. It maps unrecognized keys to `$`, range failures to `wrong-type`/`bounded-value`, and calendar-ID-array issues to a coarse wrong-type diagnosis. `tools-validation.ts` repeats schema checks and adds semantic time, ID, zone, reserved-field and create-authority checks. These are distinct layers, not all duplicates.
3. `calendar-loop.ts` persists the decision before execution, debits bounded accounting, records source/result before continuation, retains successful groups for repair, and suppresses repeated identical calls only since the last successful create; distinct pages/queries and fresh reads after writes must remain possible. `correctToolCall` can seal a fallback when repair is exhausted. Separately the model structural-rejection branch currently throws `PROVIDER_ERROR` once the budget is exhausted: do not assume every exhaustion follows the same path. User-visible completion is not proof of successful Calendar execution.
4. Embedded MCP uses the SDK against `aurvin.internal` through an in-process fetch handler, not a remote server or a socket. It validates bindings/calls, resolves targets including `primary`, gates before and after setup, lists and pins the catalogue, validates response size/discriminants and binds source, target, receipt and operation. `CalendarApiTools` performs its own current account/credential/scope fencing, timeouts and capability checks; `calendarHttp` charges just before actual fetch. The **candidate** simplification is a direct typed execution port around the existing executor, moving or retaining the response/linkage validation and target normalization that the wrapper currently owns. Catalogue wire negotiation is only necessary for the removed protocol boundary, but lifecycle shutdown/drain and in-flight/uncertain-write classification, admission, provenance and readback must survive. Measure/fixture-check each retained and removed check rather than assuming same-process implies redundant authority checks.
5. Snapshot-backed list calls can use cache or refresh via `ensureFresh` (`calendar-assembly.ts`); absence of a Google HTTP call for that model tool does not imply failure. Discovery fetches up to 100 items/page and reports page/calendar/byte/provider/unsupported-entry/primary limitations; the model-facing page contains up to 20. Do not present a partial or hidden-filtered list as an exhaustive account inventory.

### Schema authority and cursors

`calendar-tools.ts` currently keeps separate Zod `calendarInputSchemas` and hand-built `definitionsV2` JSON schemas; model body uses the latter, runtime validation the former. Existing Zod 3 is installed, but the manifest does not declare a JSON-Schema converter. Prefer no new dependency: either derive the expressible shape from a single existing authority with an auditable translation, or keep definitions with a mandatory parity test comparing every name/property/type/required/additional-properties/bounds/array uniqueness plus valid and invalid examples against the actual serialized native function parameters. Cross-field date ordering, zone, reserved keys, cursor signature/scope and authority are not adequately expressed by basic JSON Schema; document and test them as explicit semantic constraints. Changes must also account for `calendar-mcp-schema.ts`/registry if the embedded server remains. Test `{}`, null, unknown field, non-string/empty/oversized cursor, page-size/event bounds and all five tools, not just a catalogue snapshot.

`calendar-api-cursor.ts` uses HMAC with a random process-local key by default, bounded to 2048 characters, account/target/query/discovery revision and expiry (max five minutes). A snapshot-list cursor contains an offset, snapshot ID-set hash and page size; an event cursor wraps the Google page token. It is **signed, not encrypted**: its base64url payload can reveal a wrapped token, so treat the entire cursor as sensitive and never log it. Different `CalendarApi` and `CalendarApiTools` instances hold different keys. Restart invalidates existing tokens; snapshot refresh, target/query/account change or expiry also rejects them. `tools.ts` catches all list-cursor decode failures and collapses them to `CALENDAR_INPUT_REJECTED`; `calendar-api-cursor.ts` also collapses format/signature/scope/expiry. P1 needs safe distinguishable internal reason codes with no cursor value. Do not call the cursor a Google page token: if kept, make the user/model-facing contract explicitly an Aurvin continuation and document scope, refresh/restart behavior. If replaced by direct Google tokens, prove account/query binding, safe historical interpretation, budget/completeness and compatibility; do not silently reinterpret old signed cursors. If a snapshot is incomplete, its local continuation cannot resume omitted Google pages; expose limitations rather than claim completion.

## P1 diagnostic handoff

Use the existing `Telemetry`/`observedRuntime` path, not another platform. `Telemetry.inTurn` pseudonymizes stable identifiers; `event` currently allowlists only four progress phases, app error codes and a few fields, and catches synchronous sink errors. The assembled sink defaults to stdout (`app.service.ts`); normal local presentation should be readable while preserving structured records. There is an actual raw stack/error print at `backend/src/chat-runtime/durable-chat-runtime.ts:662`, outside the safe sink; touched paths must replace it with safe coded logging. This is a privacy risk observed in source, not proof sensitive data was printed during the incident.

Minimal proposed event projection, each bounded and allowlisted:

- Correlation: existing request/hashed session, turn, attempt; hashed dispatch, decision, tool-call, operation and provider request/generation identifiers when present. Never attach raw user/account/calendar/event identifiers, argument hashes that can enable dictionary attacks, or arbitrary provider IDs unchecked.
- Stage: admission, context, model dispatch/response/decision, structural or semantic validation, local cursor, authority, cache/discovery, Google request/response, correction, persistence/finalization and terminal. Fixed enums for tool, origin (`local`, `cache`, `provider`, `none`), delivery (`not-sent`, `attempted`, `response-received`, `unknown`), outcome and reason. A fetch invocation proves attempted delivery, **not** provider receipt; ensure no stale correlation when asynchronous work moves context.
- Validation: allowlisted field paths only; fixed reason class, expected constraint/type, actual JSON type and presence, no supplied value or unknown arbitrary field name. Unknown names should be `$`/redacted unless they match a known safe field. Separate malformed JSON, duplicate key/call, missing/unknown fields, invalid type/range, invalid cursor format/signature/scope/expiry, policy/authority denial, provider 400/other safe status class, and correction/budget exhaustion. Preserve local vs provider origin even if both map to `CALENDAR_INPUT_REJECTED`. Counts and finite duration should be clamped; schema revision plus fixed/fingerprinted schema is safe if content-independent.
- Terminal has **separate dimensions**: delivery status (completed/truncated/failed/cancelled), task result (success/clarification/fallback/denied/failed/uncertain/not-applicable) and write certainty (not-applicable/not-sent/confirmed/unknown). No task success solely from chat `completed`; classify user-facing fallback and interrupted/uncertain writes separately. Trace must not alter receipts, retries, accounting or durable state.

No tokens, credentials, headers, user prompts/text, private reasoning, event labels/descriptions, raw tool arguments/results, provider bodies, exception text/stacks, raw cursor or full URLs. `redactSecrets` alone is not a substitute for constructing an allowlist. Do not put variable IDs/field names in metrics labels. Sink errors must never propagate or queue unboundedly; verify disabled-detail and local-only policy/retention in the P1 runbook, including how to follow a turn. If diagnostic events themselves involve expensive async work, bound it and ensure failures cannot alter the chat.

## Historical evidence, rollout and rollback

`calendar-evidence.ts` writes versioned decision/rejection/result records in `metadata`; its v2 getters use v1/v2 compatibility decoders and expiry redaction. `calendar-compatibility.ts` defines strict v1/v2 connections, operations, receipts, sources, decisions, results and checkpoint references; checkpoints validate scope and prohibit sensitive keys (`calendar-checkpoints.ts`). `calendar-context.ts` checks tool groups, account revisions and expiry. Saved graph state contains versioned cursor/references and uses saved results for finalization/recovery. `calendar-operation.ts`, recovery and publication paths protect accepted intent, persisted operation state, receipts, readback and uncertain outcomes. Stored record existence/content has **not** been inspected and historical compatibility is not proven simply by these decoders.

P2 should prefer leaving durable v1/v2 shapes and tool names readable while simplifying only the execution seam. If changing model-visible arguments or result structure, do not mutate strict v2 schemas in place and thereby make old records unreadable: plan versioned decoders/translation, distinguish historical replay from authority to execute, preserve source redaction/expiry and terminal v1 read-only behavior. For an in-flight old decision, choose explicitly between a provably safe compatible continuation and a safe interrupted/clarification outcome; never issue a new write or inference merely to recover a saved result. Old cursors are already invalid after normal restart; fail safely with an actionable restart-page instruction rather than accepting them as Google tokens. On rollout/rollback, test both directions with versioned fixtures, pending and completed writes, old checkpoints and cursor restart; a prior binary may not parse newly written shapes. If backward reading by the old binary cannot be proven, drain active work and block rollback or use a documented reversible staged strategy; never delete conversations, receipts, checkpoints or records as a workaround. No persistent-schema change should ship without this explicit strategy.

Until then record live **unrun/blocked**, or an explicit implementation-only waiver, never resolved from offline fixtures.

## Key unresolved issues

1. The exact incident decision, rejected arguments and boundary are unknown; P1 must provide evidence before P2 behavior changes.
2. `owner` manager role versus data-owner evidence and email/alias ambiguity must be resolved honestly in the model result and acceptance wording; Google documentation does not establish a complete owner classification from role alone.
3. The current signed-cursor contract is not Google's token contract and signed payloads are not confidential. Decide whether to retain with truthful naming and compatibility, or replace only after proving equivalent isolation and safe rollout.
4. Google Calendar APIs can omit fields and return partial/empty pages; verify fixture shapes against documentation. `calendar-discovery-api.ts` requests a restricted fields mask without `kind` but treats absent `items` as empty only when `kind` is present; whether a real empty masked response triggers this branch is an **unverified hypothesis**, not incident evidence.
5. Developer Preview eligibility, real schema/role behavior, provider outages, selected-model correction behavior, native topology and actual stored data remain untested; no live or database evidence was collected.
